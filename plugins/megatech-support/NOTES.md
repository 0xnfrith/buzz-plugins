# Megatech support: notes

What works through the plugin API, what the plugin does not do, what was verified and what was not. Read `docs/building.md` first; this page is the part that is particular to this plugin.

## What it is, and the status

An MVP built **against a mock**. The service it talks to is run by another team and has no address yet, so the origin is a placeholder (`https://support.megatech.invalid`; the `.invalid` top-level domain never resolves) kept in one constant, `src/support/origin.ts`, and in the manifest's `host.networkOrigins`. A test checks that the two are the same. **That is the one open seam:** the placeholder and the manifest stay as they are until the service has a real address, and the two change together. The contract below is a **proposal**: the service's team has not agreed it yet. The plugin does nothing useful until the hosted service exists and the origin is changed.

**Tested against two Buzz commits.** The design was written against block/buzz-app `d92bfb2c`, the commit CI runs the browser spec on. The identity route, the host's request fields and the plugin API this plugin uses were read again against `5a7f4952` (see "Checked again" below), `src/buzz.d.ts` is trimmed from that commit, and the browser spec was also run on it (20 of 20), which is where the screenshots in the README come from. CI stays on `d92bfb2c`.

## Works on any relay

Nobody needs a Megatech relay, a Megatech account or any relay at all in particular. The plugin is for anyone with a Buzz key.

- **It reads one thing of the relay: the signed-in key** (`relay.snapshot().viewer`), and it listens for that to change (`relay.subscribe`). It reads no relay address, community, channel, member list, membership or event. Tests scan the source for it (including taking the relay apart, indexing it or keeping it under another name, and any use of `ctx.relay` outside `src/index.tsx`) and record every property read on the relay and on its snapshot through a whole session (`test/unit/any-relay.test.ts`). The scan is a text match, not a proof: code that reaches the relay in a way it does not look for would need a new rule.
- **The service is sent nothing of the relay either**: the public key, the signature, and what the person typed. The same test file lists every request's fields and headers.
- **There is no tier, plan or account switch in the plugin.** What it does today is the free subset: Ask, Open a ticket, My tickets, the Settings card, and the two tools and the agent type (off by default). Everything is keyed by the verified Buzz key and nothing else. What a key may see beyond its own tickets is the service's rule, not the plugin's. Nothing for billing is built.
- **A key the service has never seen is a new person**, not a refusal. This is a rule of the proposed contract (see "The contract"), and the fake service carries it out.
- **Two things depend on the person's setup, on any relay.** The key is known only while Buzz is connected to a community (or has resumed one), so Verify before that says so. And an agent of the support type posts in the channel where it was mentioned, on whichever relay the agent was made on, where everyone who can read the channel reads the answer; creating an agent also publishes its profile there. It is off by default, and the Settings card says it.

## Design

- **One page** (`Megatech support`): Ask, Open a ticket, My tickets. Before the identity is verified the page shows one card that says what pressing **Verify** does, and nothing is sent until it is pressed.
- **One Settings card** (Settings, Plugins, Megatech support): the identity (Verify, Verify again, Forget) and the **agent switch**.
- **One origin**, reached only through `ctx.host.request` (Buzz's own HTTPS client: it refuses any other origin and follows no redirects). No commands, no processes, no files.
- **Verify again fails closed.** Pressing it while verified starts a new check; the page shows the Verify card while it runs, and if the new check fails the session that was held is dropped too, rather than kept on a footing the service has just refused. What was typed in the forms is kept above the card, so it is still there afterwards.
- **The session belongs to a key.** It ends, with a reason, when a **different** key is signed in than the one it was verified for (the identity asks at each use, and watches the relay), and the service is told. A signed-in key that is merely absent is not a different key: Buzz's snapshot has no `viewer` while the relay connects, after a disconnect and in some error states, so a sleep, a dropped network or a community switch keeps the session. While the key is unknown the tools refuse (fixed words: Buzz has not said which account is signed in), since the plugin cannot then confirm it is still the same person. A code may live at most ten minutes (`expires_in` is capped at 600; the contract says five), since the attestation has no expiry of its own.
- **Forget, a lost session and leaving.** Forget (and the plugin being switched off) end the session here at once and ask the service to end it; a session the service says is over, or whose time is up, ends with a reason the page shows. A check that is still running when any of these happens keeps nothing.
- **Fixed error text.** Every failure shows one of a few fixed sentences (`ERROR_TEXT` in `src/support/client.ts`, and the identity check's own in `src/support/identity.ts`). The service's own wording, and the host's, are never shown, kept or logged, since a service's error can repeat what it was sent.
- **The session token is in memory only.** It is never persisted, rendered, logged, put in a URL or in an error; it goes into one `Authorization` header. Closing Buzz, disabling the plugin or pressing **Forget** ends it here, and Forget and disabling also ask the service to end it (`POST /v1/identity/logout`, answer ignored). The only thing the plugin keeps in `localStorage` is the agent switch (`megatech.support.agent.v1`).

## The identity check: why it uses the owner attestation

The design first meant a signed one-time challenge that the plugin would publish as an event. That cannot be done, for the reasons below, so the proof is Buzz's owner attestation instead. The reasons were read in Buzz's source and are written down here (with the commit) so the choice can be checked, and checked again when Buzz changes.

A plugin cannot sign anything itself, and Buzz gives it no signing call. Buzz's own relay service says so in a comment: "Plugins receive read models, never a signer or transport". What the host object does have is `prepareRemoteAgentAuthorization(agentPubkey)`, which Buzz's hosted agents use. It returns the signed-in user's **owner attestation** (NIP-OA), `["auth", owner, "", sig]`: a BIP-340 signature by the user's key over `sha256("nostr:agent-auth:" + agentPubkey + ":")`. It needs no manifest declaration and shows no prompt. This plugin uses it as a login proof:

1. `POST /v1/identity/challenge {pubkey}` returns a one-time code and how long it lives, in seconds (`expires_in`, five minutes). A length of time, not a date, so the plugin never compares its clock with the service's.
2. The plugin computes `N = sha256("megatech-support:v1:" + code)` (lowercase hex) and asks Buzz for the attestation over N. It sends **only N**, never the code and never a value the service chose.
3. `POST /v1/identity/verify {pubkey, challenge, auth}` sends the attestation. The service recomputes N from the code it issued, checks the signature against the key that asked, checks that the tag is exactly `["auth", pubkey, "", sig]`, and that the code is unused and fresh. A code is spent by its first use, right or wrong. It then answers with an opaque session token (about an hour).

**What is repurposed.** An attestation is an authorisation: "this key may act as my agent". Here it is a login proof.

**Why it is inert.** N is a hash of a code the service issued. Nobody holds a key whose public key is N, so the attestation authorises nobody to do anything. The plugin computes N itself, so even a service that sent a public key it holds, as its "code", would be handed nothing: N would be a hash of it. The service must never accept N as a key (N is never a pubkey), and must accept an attestation only for a code it issued, once, within five minutes. Empty conditions mean the attestation is **unconditional**: no expiry and no kinds. So its safety rests entirely on N being a hash nobody holds a key for, and the limits above are the service's to enforce. A unit test has a hostile service send a key it holds, the user's own key and look-alike fields, and checks that Buzz is only ever asked to sign the plugin's own hash.

**What Buzz does and does not do.** The call takes no conditions: Buzz always signs with empty ones, and its own code rejects any other form, so there is nothing to narrow. It publishes nothing. The plugin never sees a key.

**Fail closed.** The check fails, with fixed words and with nothing sent to the service's verify, if the host has no such call, if it throws or does not answer within 20 seconds, or if its answer is not exactly a four-item tag of `"auth"`, the signed-in user's key, `""` and 128 lowercase hex characters. Each of those has a test (`test/unit/identity.test.ts`).

**The risk.** The call is not in Buzz's plugin documentation: it is typed on the host object as optional. Block could restrict it or change what it returns. If it goes, the plugin stops verifying (it does not fall back to anything weaker) until it is changed. Any other installed plugin can ask for the same attestation, which is the model of unsandboxed plugins: a plugin is trusted code in the app.

**Fallbacks, not built.** B: a visible signed message. The plugin can publish an event through the host's outbox and send the signed event, but every kind a plugin may publish is a visible chat or status event. The kinds that would be invisible are closed to plugins: the ephemeral kinds (20000-29999) are not in `nativeWriteKinds`, and kind 30078 is listed there but `relay_sign` refuses it ("Channel recipe or Canvas rejected"). It was found by reading `nativeWriteKinds` and `relay_sign` in block/buzz-app, and confirmed read-only with `outbox.supports()` in the installed app. C: no identity at all, so no account data. The identity call is behind one interface (`Prover` in `src/support/identity.ts`) so either could replace it.

### Checked again against block/buzz-app `5a7f4952`

Read in source (the desktop app was not run for this check). Everything above still holds:

- **The call is there, optional on the `Host` type, and needs no manifest grant and shows no prompt:** `src/features/host/service.ts` (`prepareRemoteAgentAuthorization?` on `Host`, the implementation, and the `HostService` method, which checks no manifest). Its own tests call it from a plugin-scoped context with no declaration (`service.test.ts`).
- **The answer is exactly `["auth", owner, "", sig]`:** four items, empty conditions, 128 lowercase hex; the host itself throws otherwise. The native signer signs `sha256("nostr:agent-auth:" + agent + ":")` with the user's key (`src-tauri/src/identity.rs`, `authorize`; the browser broker does the same in `browser-host/relay-broker.mjs`). It refuses an agent key equal to the owner's, which N, a hash, never is.
- **Still no signer for plugins:** `src/features/relay/service.ts` says "Plugins receive read models, never a signer or transport", and there is no NIP-98 or other signing call on the host. `nativeWriteKinds` (`src/features/relay/native.ts`) holds no ephemeral kind, and `relay_sign` (`src-tauri/src/relay.rs`) still refuses kind 30078. Both are as they were at `d92bfb2c`.
- **New since `d92bfb2c`, and why it matters here:** Buzz's `docs/identity.md` now describes an "Authorize external identity" screen that uses this same call, and warns that the key it signs for "can direct the owner's coding agents to run commands as them". That is the reason the plugin only ever asks over a hash nobody holds a key for, and never over a value the service chose. And a manifest can now carry a `host.federatedIdentity` grant (`docs/plugin-architecture.md`); it is documented for Buzz's own sign-in and is a session with that sign-in server, not a way to prove identity to another service. Neither changes the route.

## The contract (proposed)

```
POST /v1/identity/challenge   {pubkey}                      -> {challenge, expires_in}       expires_in: seconds, 10 to 600 
POST /v1/identity/verify      {pubkey, challenge, auth}     -> {session, expires_in}         expires_in: seconds, 10 to 86400
POST /v1/identity/logout      (no body)                     -> anything; the plugin ignores it
POST /v1/ask                  {question}                    -> {ticket_id, answer?}          Idempotency-Key header
POST /v1/tickets              {subject, body}               -> {ticket_id, status}           Idempotency-Key header
GET  /v1/tickets                                            -> {tickets: [{ticket_id, subject, status, updated_at}]}
GET  /v1/tickets/{ticket_id}                                -> {ticket_id, subject, status, updated_at, messages: [{from, at, text}]}
```

JSON in and out; `Authorization: Bearer <session>` on everything except the first two (and logout, which only needs the session it ends); errors are an HTTP status (401 unknown or ended session, 403 identity refused, 404 no such ticket, 422 or 400 unusable input, 429 with `Retry-After`, 5xx) with a body the plugin ignores. Limits the plugin keeps to: question 4,000 characters, subject 200, body 8,000; ticket ids start with a letter or digit and are `[A-Za-z0-9._:-]{1,64}` (so `.` and `..` are not ids); an answer or a message up to 20,000 characters; 200 tickets and 500 messages. `from` is `you` or `support`. `ask` always leaves a ticket behind and returns its id, with `answer` only when the service had one within the call (the plugin's deadline is 170 seconds on a Buzz that takes `timeoutMs` and 30 on an older one; see "How long `ask` waits" below). A retry of `POST /v1/ask` or `POST /v1/tickets` with the same `Idempotency-Key` returns the same ticket. The plugin keeps a key for a question or form that has not succeeded yet, so its retry (by the person, or by an agent whose call timed out) is the same ticket; different text, or the same text once it has succeeded, is a new key.

**A key the service has never seen is a new person (proposed rule).** The proof is the only thing that decides whether `verify` succeeds: a key with no account, no history and no relationship to Megatech verifies like any other, gets a session, and has an empty ticket list. A `403` from either identity call means a failed proof (a code the service did not issue, or spent, or past its life; a signature that does not check; a key that is not the one that asked) and never "unknown key". The plugin shows the same fixed words for any refusal, so it could not tell the two apart; a service that refused unknown keys would shut out exactly the people this plugin is meant for. Any further limit on what a key may see is the service's rule, applied to the session after it exists. The fake service carries this out and `test/unit/any-relay.test.ts` shows it.

**How long `ask` waits.** `POST /v1/ask` may take up to the plugin's deadline of 170 seconds (`ASK_DEADLINE_MS`), and a reply within it is returned with the ticket. The host's own limit is 30 seconds unless a request names another (`timeoutMs`, 1 to 180000), so `ask`, and only `ask`, sends `timeoutMs: 170000`. Past it the plugin gives up with "could not reach", and the ticket the service made is still there: asking again with the same key is that ticket. **The version boundary:** `timeoutMs` was added to Buzz in `b86b9f3c` and first shipped in desktop-v0.7.0-beta.1. A Buzz from before that refuses the whole request for the field it does not know (its request type has `deny_unknown_fields`), as a validation error before anything is sent. The plugin then sends the same `ask` once more without the field, under the same `Idempotency-Key`, and remembers not to send the field again. It never repeats a request for any other failure: a timeout or a network error may mean the request arrived. On such a Buzz `ask` waits the default 30 seconds. Both cases are tested in `test/unit/client.test.ts`.

`auth` is the four-item attestation tag. The service's rules, which `test/fake-support/server.mjs` carries out and `test/unit/service-check.test.ts` lists: **N is never a pubkey; an attestation is accepted only for a challenge the service issued, once, within 5 minutes.**

## The agent type and the tools

- **Off by default, and only when the plugin starts.** The agent type `megatech.support/support` and the two tools are added only when the saved switch is on **as the plugin starts**; `apply` reads it once per start. A start is Buzz starting, and also the plugin being turned off and on or updated: the card and the README say so, and say that agents running then start their sessions over. Why not live: an agent session lists its tools when it starts and replaces itself when the list changes (a Codex agent starts a new thread and loses its context), so adding or removing tools while Buzz runs would do that to every agent on the device. Turning the switch off afterwards stops the tools and the type at once, though they stay listed until the restart: each call asks the saved switch.
- **Tools** (`megatech_support_ask_or_open`, `megatech_support_ticket_status`): an agent may call them while the switch is on, the identity is verified and **the agent is the verified person's own**: `client.owner`, the owner Buzz records for the agent, has to equal the key the session is verified for (an agent with another owner, or none recorded, gets a fixed refusal and nothing is sent); otherwise they get a fixed error that says to verify first, or that the plugin is off. **What is left:** a tool cannot tell who asked the agent, so an agent that answers someone else in a channel can pass on what a tool returned to them. The card and the README say so. `ask_or_open({question})` returns `{ticket_id}` and `answer` when there is one; `ticket_status({ticket_id})` returns `{ticket_id, status}`. Their names, descriptions and schemas are frozen by a test, for the reason above. The names start with the plugin's, as `docs/agents.md` asks, and a name another plugin already has is caught, so the plugin still loads and the card lists what was not added.
- **The type has no model.** A type with `run` runs our code, not a language model, and the tools are only handed to harness sessions (Claude, Codex, Goose, Pi). So the support type's `run` answers a mention with the same code as `ask_or_open`, and replies in the thread as the agent (the thread root by Buzz's own rule: `root` with `reply`, else `reply`, else the mention itself; a quote tag is not a root). A mention is read the way Buzz writes it, `[@Name](nostr:npub1…)`, so "status T-12" is a status question. What it posts into the channel of support's answer is cut at 4,000 characters, with the ticket named for the rest, since every member reads it. It answers **only the owner's own mention** (anyone in a channel can mention an agent, and the answer would come from the owner's verified session; Buzz's own agent types make the same check and its documentation asks every type to). `run` is tested with fakes in `test/unit/agent.test.ts`; the web build checks that the type is registered, not that it runs. It has **not** been run by a real harness session.

## What was verified

Where, and against what: `test/unit` (Node, vitest) and `test/web/support.spec.mjs` (the web build of block/buzz-app, headless Chromium, run by `test/run.sh`; CI runs both, the spec on `d92bfb2c`, and it was also run by hand on `5a7f4952`: 20 of 20). In the real desktop app on Linux (see the README for the version): see "In the real app" below.

- Every request goes to the one origin; the session is sent only in `Authorization`; the identity calls carry no credential; nothing is sent before **Verify**; ask, open (once, even after a failed try), list, read, refresh; a lost session returns to the Verify card; fixed text for every error class, with the service's own words never on the page.
- Forget, a lost session or switching the plugin off while a check is running: the check keeps nothing and starts no timer (and tells the service if its answer arrives late); a late 401 for an old session does not end a newer one; a session that ends in the middle of a form says so and keeps what was typed.
- The attestation the service verifies is the one the host returned, over N, with a real BIP-340 check in the fake; Buzz is asked about exactly one value and it is a hash.
- The check fails closed for each wrong form of the host's answer, a missing call, a host that fails and one that never answers.
- Agent type and tools: not added when the switch is off (nothing saved, `off`, or any other word), added once when it is on as the plugin starts, usable by the user's own agents (the owner Buzz records for the agent is the verified key) while the switch is on and the identity verified and Buzz confirms which key is signed in, refused with fixed words otherwise (switched off, not verified, Buzz not saying which key is signed in, not this person's agent), with no request made.
- No `fetch`, WebSocket, `eval`, remote image or other way out of the page in the source (a test scans it); nothing in storage but the switch; the one call that signs for the user is in one file.
- Any relay: the source reads nothing of the relay but the signed-in key (a scan, and a record of every read through a whole session); every request carries only the contract's fields and headers; a key the service has never seen verifies, asks, opens and lists (`test/unit/any-relay.test.ts`).
- The ask deadline: `ask` carries `timeoutMs: 170000` and no other request does; an older Buzz's refusal of the field gets one more try without it under the same key and is remembered; a timeout, a network error, a refusal of another field or a complaint about the value is never tried again (`test/unit/client.test.ts`). The browser spec checks the first part through the page: the two questions it asks carry the deadline and no other request does (a deadline changed to 30 seconds fails it). The web build has no native request, so the browser spec cannot show what the real host does with the field.
- The identity route, the host's request fields and the write rules, read in Buzz's source at `5a7f4952` (see "Checked again" above).

## What was not verified

- **Against a real service.** There is none yet. The contract is a proposal, and so is its rule about a key the service has never seen.
- **An agent using the tools against a real model, and an agent of the support type.** Neither has been run in Buzz: the tools and the type are tested with fakes (`test/unit/agent.test.ts`) and the web build checks that the type is registered. Running them needs an agent harness with model access inside Buzz, which has not been available; creating an agent also publishes its profile on a relay.
- **The exact refusal of an older Buzz.** The fallback for `timeoutMs` depends on how a Buzz from before that field words its refusal. No such Buzz was run: the text in the tests is serde's usual form ("unknown field `timeoutMs`, expected one of ..."), written by hand, and the pattern allows quotes, backticks or a colon between "unknown field" and the name. If the real words differ more than that, the plugin does not send the request again and `ask` fails with "could not reach" on those Buzz versions until the pattern is changed.
- **The desktop app, for this change.** The browser spec and the screenshots are from Buzz's web build. The desktop app was not run for this change; its earlier run is the one under "In the real app".
- **macOS and Windows.** Linux only, and the web build.
- **The web build's own host call.** The browser tests give the plugin a fake host for the attestation (the web build's broker does not serve it); the real call ran only in the desktop app.
- **`timeoutMs` in the desktop app.** The request goes through a fake host in the tests. Whether a real service can hold a call for 170 seconds through Buzz's client has not been tried.
