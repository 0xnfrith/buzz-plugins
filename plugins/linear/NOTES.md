# Linear for Buzz: notes

What the plugin API reaches for a board like this, how it was tested, and what was not. Written against block/buzz-app at commit `c2210b45` (main, 2026-10-23) and the Linear GraphQL schema at linear/linear `618a737a` (2026-10-21).

## Verdict

A working board fits inside the documented API with very little reaching into the page: one page, one settings card, the host's HTTP client for Linear, and the macOS Keychain (through a declared `security` command) or `localStorage` for the key. The gaps are the usual ones (no plugin storage, no credential store, no drag service, no stylesheet service) and each has a small, tagged workaround.

## What goes through the plugin API

| Need | Route |
| --- | --- |
| A page in the sidebar, with an icon | `ctx.pages.register({ primary: true, layout: "workspace", icon })`. The icon is a one-shape, one-colour board of three columns as a `data:image/svg+xml` URL (API v1 ships no assets); see the next table for how it takes the theme's colour |
| A place for the key | `ctx.settingsCards.register({ group: "Plugins" })` |
| Reaching Linear | `ctx.host.request` with `host.networkOrigins: ["https://api.linear.app"]` in the manifest. HTTPS only, that exact origin, no redirects, 1 MiB request body, 16 MiB response, 30 s deadline. The `Authorization` header is allowed |
| Opening the settings card from the page | `ctx.navigation.open({ version: 1, kind: "settings", section: "megatech.linear/settings" })` (a grouped card's section id is `plugin/card`) |
| Light and dark | Host CSS tokens (`--surface-base`, `--surface-panel`, `--border-standard`, `--text-standard`, `--text-metadata`, `--affordance-row-hover`, `--green-9`, `--purple-9`, `--red-9`, `--amber-9`), so the board follows Settings, Appearance with no listener |
| Opening Linear and GitHub | Plain `<a target="_blank" rel="noopener noreferrer">`, as the bundled pages do |

## What is outside the API, and what we do

All tagged `[DOM]` or noted in the code.

| Need | Why there is no API route | What we do |
| --- | --- | --- |
| Stored data (key, last team and filter) | "Plugin-specific persistent data has no host API yet", and the host has no credential store | `localStorage`, key `megatech.linear.board.v1` for the team and filter. The API key goes to the macOS Keychain through three declared `security` commands (next section); where there is no Keychain it is `localStorage` too, `megatech.linear.api-key.v1`, in plain text that any other plugin can read, and the card and README say so |
| Styles | API v1 has no separate CSS | One `<style data-megatech-linear>` added and removed inside `ctx.effect` |
| Drag and drop | No drag service. HTML5 drag events work (Buzz turns `dragDropEnabled` off) but give no control over the dragged copy, scrolling or cancel | Pointer events on `window` while a press is held, a threshold, a floating copy of the card, edge auto-scroll, Escape to cancel, and the click that ends a drag suppressed. Mouse and pen only; touch scrolls. A keyboard route is the **Status** menu in the details |
| Clearing a text selection while dragging | The host has no selection service | `getSelection().removeAllRanges()` while a drag moves, behind `-webkit-user-select: none` (WebKit needs the prefix) |
| The page icon in the theme's colour | The host draws a page's `icon` as an `<img src="data:…">`, and an image cannot take `currentColor` from the page | One rule in the plugin's `<style>`, matching only an `<img>` whose `src` is exactly this plugin's icon: it paints the same shape through a CSS mask in the entry's text colour and moves the image's own pixels out of its box. If a later host draws the icon another way the rule stops matching and the icon is simply a plain dark one. (The MEGATECH lockup in the page header is ordinary page content and is not affected.) |
| Colours of the brand | Tokens carry no brand | Cyan `#00d4ff` on dark and `#0090b8` on light, chosen by the host's `data-color-mode` attribute |

## Linear: what was relied on

- Auth: a personal API key goes in `Authorization` as is. `Bearer` is for OAuth tokens. **Confirmed against a real workspace:** the key as is is answered with 200; the same key behind `Bearer` is refused with HTTP 400 and the code `INPUT_ERROR` (not 401), which the plugin shows as "Linear did not accept the API key." like any other refusal.
- **A pasted key is checked before it is kept.** Linear is asked first. A key it refuses is never saved. When a key is already saved and Linear cannot be asked (unreachable, a 5xx, rate limited), the saved key stays, nothing is saved and the card says "Your saved key is unchanged; try again"; only when there is no key yet is a key saved unchecked, and the card says so. Seen in the real app with the host blocked by a local proxy: see "What was verified".
- **Errors shown are fixed text.** Whatever Linear says in a GraphQL error (`message`) is never read, let alone shown: a service's error text can repeat what it was sent, the key among it. Each kind of failure has its own sentence in `client.ts`, and a test fakes a reply that echoes the key and checks it appears nowhere (the error, the board's notice, the page, the console).
- **Colours from Linear** (labels, projects, states) go into a `style` or an SVG attribute only if they are `#rgb`, `#rrggbb` or `#rrggbbaa`; anything else (a `url(...)` would be a remote image) is drawn in a neutral grey. Linear sends hex, so this is defence only.
- Every document is validated against Linear's published schema in a unit test, so field and variable-type mistakes fail before a user sees them. `IssueFilter` ids are `ID`, while `team(id:)` takes `String!`, so `TeamSetup` has two variables.
- One request per column (`issues(filter: team + state [+ project])`, 50 a page, newest change first) rather than one big list, so a long Done column cannot starve the others and each request stays small. (Whether each stays under Linear's complexity limit is not confirmed; see below.) A saved view goes through `customView(id).issues`, so Linear applies the view's own filter.
- The refresh timer asks one cheap question (`issues(filter: team + updatedAt > watermark, first: 1, orderBy: updatedAt, includeArchived: true)`) and reloads only on a yes. The watermark is the largest `updatedAt` seen so far, from loaded issues, from the plugin's own moves and from the probe's answer, so clock skew cannot cause a loop, the plugin's own moves are not news, and a change outside the chosen project or beyond the loaded page triggers one reload, not one a minute. An empty board has nothing to measure against and uses the local clock minus a minute. Ticks closer than two seconds apart count once (the window coming back fires several events).
- A read that began before a move cannot undo it: every move bumps a counter, and a load keeps any card moved after the load began. A saved project or view that no longer exists drops back to all issues with a note.
- Sub-issue progress is the sub-issues of state type `completed` over all that are not `canceled`. PR chips come from GitHub attachments whose URL is `…/pull/<n>`; the state of a PR is read from `metadata.status` and `metadata.draft`. **Checked in a real workspace:** an attachment made through the API with a `github.com/…/pull/<n>` URL has `sourceType: "unknown"` (so the plugin finds PRs by URL, never by `sourceType`), and the `metadata` sent with it comes back unchanged, so the chip and the details show it. **Not checked:** what Linear's own GitHub integration writes into `metadata` for a real pull request, since the test workspace has no GitHub integration.
- Ordering inside a column is the issue's `sortOrder` ascending for open states and `updatedAt` newest first for Done, Canceled and Duplicate. **Observed in a real workspace:** a newly created issue, and an issue moved to another state through the API, gets a `sortOrder` lower than the others in its state (for example -848, then -1919, then -3838 for three created in a row, against 81 for the first), so ascending order puts the newest at the top, as the board does. What was not seen is Linear's own board: no browser session on Linear's site was used, so "lowest first" there is inferred from new issues arriving at the top, not looked at.
- **Duplicate is a state type of its own.** Every new workspace has a state named Duplicate, and the API gives it the type `duplicate` (the schema lists it beside the other six) and lists it first, before Backlog. The board puts it last, orders it by last change like Canceled, leaves duplicates out of sub-issue progress, and draws it with Canceled's glyph; a state type it has never heard of sorts after the known ones instead of scrambling them. **Checked in a real workspace:** an issue cannot be created in it, and a move into it is refused ("missing duplicate relation"): Linear puts an issue there only when it is marked a duplicate of another (an `issueRelationCreate` of type `duplicate` did exactly that, with no state change sent). So the board does not send that move: a drop on the Duplicate column says why, and the Status menu shows Duplicate greyed out.
- **Cost and limits, measured with a personal key in a real workspace.** `X-Complexity` was 17 for one column request (Todo, 8 issues, `first: 50`), 3 for the refresh probe and 412 for the team setup (states, projects and views). The headers `X-RateLimit-Requests-Limit` and `-Complexity-Limit` said 2,500 requests and 3,000,000 complexity points per hour, and the `-Reset` headers are milliseconds since the epoch (the plugin reads seconds or milliseconds). A board load is one setup request and one per column; an idle board costs one probe a minute, so about 60 requests an hour.

## The key and the system's store

The key opens the person's Linear, so plain `localStorage` is not the default where something better can be reached (`docs/building.md` §4). Two stores are used, each through three commands the manifest declares, with fixed arguments, all naming one item:

| System | Store | Commands (ids) | The item |
| --- | --- | --- | --- |
| macOS | the Keychain | `security find-generic-password … -w`, `add-generic-password -U … -w`, `delete-generic-password` (`keychain-read`, `-save`, `-delete`) | service `buzz-linear`, account `linear` |
| Linux | the Secret Service (gnome-keyring, KWallet, …) | `secret-tool lookup`, `store --label=…`, `clear` (`secret-read`, `-save`, `-delete`) | attributes `service buzz-linear`, `account linear` |
| anything else | none | | the key is plain text in `localStorage`, said so in the card |

The Keychain mechanism is Beeper's (`plugins/beeper/NOTES.md`, "The token and the Keychain"), with Linear's own names and Linear's rules on top; the Linux one follows the same pattern.

- **Which store.** `detectStore` (`keys.ts`) reads `navigator.platform` and the user agent: a Mac is the Keychain, Linux (not Android) is the Secret Service, the rest have none. "Not reachable" is not detected on its own: `runCommand` reports every failure as `null` (non-zero exit, timeout, program missing), so a store counts as unreachable when a save is not confirmed by the read-back.
- **Read once, held in memory.** `keys.ready` reads the store when the plugin starts (then the profile, if the store has nothing); a request waits for it (`readKey` may be a promise) and then asks the cache, so a poll never starts a program. "Check Keychain" in the card reads again.
- **Saving keeps #23's rules, then the store's.** Linear is asked first. A key it refuses is never saved. With a key already saved, a key that cannot be checked (unreachable, 5xx, 429) saves nothing. Only a key Linear accepted (or a first key that could not be checked, said so in the card) goes on to the store. On a Mac that is `add-generic-password -U -s buzz-linear -a linear -w` with `-w` last and no value, which asks for the password and then for it again: the key is written twice, one line each, on standard input. On Linux it is `secret-tool store`, which reads standard input to the end and keeps what it gets (a trailing line break too, as seen), so the key is written once with no line break. Then the item is read back and compared: what the real programs do with a piped standard input is partly an assumption (below), and exit status is not trusted. Only after the read-back matches does the card say "saved", the plain copy go and the board start over.
- **When the store does not confirm the save:**
  - **macOS:** nothing is kept, a saved key is as it was, and the card shows the one command to run in Terminal and a **Check Keychain** button. There is no plain fallback on a Mac (Beeper's card offers "keep it in the profile instead" there; Linear's does not).
  - **Linux:** the key goes to the profile as plain text, and the card says so with the reason; the next start tries the store again and moves it. The exception: if the store already holds a key, a replacement it will not take is *not* kept in the profile, because at the next start the store's key is read first and the stale plain copy is deleted, which would silently lose the replacement; the saved key stays and the card says so.
- **The move out of the profile.** A key already in `localStorage` (saved by an earlier version) is moved at the first look: save, read back, and only then delete the plain copy. If the store will not take it, the plain copy stays, is used, is labelled plain text in the card (with **Move to Keychain** / **Move to secret store**), and the move is tried again at every start. After a move there is no plain copy, so there is nothing to repeat. If the store already holds a key when a plain copy is found, the store's is the one that counts and the stale copy is deleted (a crash between "saved" and "deleted" leaves both with the same key).
- **Remove key** deletes the store's item and any plain copy, then reads the store again; if it still gives the key, the card says so and the key stays in use.
- **Never silent:** the card always says which place holds the key (the store by name, or "this app's profile, as plain text" with the reason).
- **Not `security -i`**, which reads commands from standard input and would keep the key off the command line too: a declared command that takes any subcommand would let the plugin do anything with `security`, and the install review could not say so. The commands are narrow and the review lists every argument.
- **What it does not protect against:** the item is made by `security` or `secret-tool`, which are then allowed to read it, so another plugin that declares the same program could read it too; the difference from `localStorage` is that the declaration shows in its install review, where reading `localStorage` needs none. It does protect against the profile's files, backups and anything else that can read them but cannot run the program. On Linux, any program of the user's session can read an unlocked Secret Service; that is the system's model.

**Seen on Linux** (libsecret-tools 0.21.4, an unlocked gnome-keyring on the session bus, by running the program): `store` reads standard input to the end and keeps a trailing line break; it replaces an item with the same attributes; `lookup` prints the secret with no line break and exits 1 when there is none; `clear` exits 1 when nothing matched. With a private bus and no keyring (a nonexistent bus address) `store` and `lookup` fail, which is the unreachable case.

Assumed about macOS's `security`, **none of it seen on a Mac** (there was none):

1. `find-generic-password -s S -a A -w` prints the password and a line break, and exits non-zero when there is no item (the plugin only needs: no output).
2. `add-generic-password … -w` with `-w` last asks twice: Apple's source (`SecurityTool/macOS/keychain_add.c` in apple-oss-distributions/Security) calls `getpass()` for "password data for new item:" and again for "retype password for new item:", up to three tries, so two matching lines are right. `getpass()` reads the controlling terminal first and falls back to standard input only when no terminal can be opened. So when Buzz is started from Finder or the Dock (no terminal) the lines on standard input are read; when it is started from a terminal the child may inherit that terminal and wait on it until Buzz's five-second deadline kills it. That case is not believed to work; the read-back turns it into "not kept" plus the Terminal command, never into a false "saved".
3. An item made by `security` can be read by `security` without a prompt. If macOS does ask, the read has Buzz's five-second deadline: a read that times out looks like "no key", and **Check Keychain** reads again.
4. `-U` updates an existing item.

**How it is tested.** `test/fake-security/security` and `test/fake-secret-tool/secret-tool` are stand-ins that behave as above (and, on request, refuse, wait, hang, keep something other than what they were given, or will not delete), and `test/host-sim.mjs` runs the manifest's commands as real processes the way Buzz does (no shell, stdin only where declared, a deadline, a size limit, `null` on any failure). What that proves is how the plugin treats a program that behaves so: the key only on standard input and never in an argument (checked in the process list while the program runs, and in the log of every call), checked by reading back, a refusal, a missing program, a mismatch and a hang reported or fallen back from as designed, and a key from the profile never lost on its way. `test/unit/secret-service.real.test.ts` runs the same store against the **real** `secret-tool` and a real Secret Service where one exists (`LINEAR_REAL_SECRET_TOOL=1`; the "Linear key store on a real Secret Service" job of `.github/workflows/linear-tests.yml` runs it under a headless gnome-keyring on a private bus); it refuses to run over an item that is already there. There is no macOS runner, so the Keychain is only ever tested against its stand-in.

## What was verified, and how

Run against the code in this folder. CI (`.github/workflows/linear-tests.yml`) runs only the type check and the unit tests; everything else below is run by hand.

- `pnpm test` (vitest, 118 tests, and 4 more that run only where a Secret Service does): the key store against the real processes of the manifest's `security` and `secret-tool` commands (stand-in programs), against the real `secret-tool` (the 4, with `LINEAR_REAL_SECRET_TOOL=1`), which store a system has, the client (headers, error kinds, fixed error text, no key in any error text, even from a reply that echoes it), what is done with a pasted key when Linear can or cannot be asked, colours from Linear, the store (load, paging, filters, optimistic move and rollback, refresh rules, stale answers dropped, blocked states, no request for a move into Duplicate, no tick before the time Linear gave after a rate limit), the column order and the progress count with the Duplicate type and an unknown one, the page icon and its mask rule, and every GraphQL document against Linear's schema.
- `test/run.sh <block/buzz-app checkout>`: 55 browser tests in Buzz's own production web build (headless Chromium, fixture relay), with the plugin registered the way an installed one is. They cover the columns and their order (Duplicate last), drag (including Escape, a refused move and a drop on Duplicate), the details panel and its keyboard route (Duplicate greyed out in the Status menu, and greyed out as a target while a card is held), the connect-and-save flow, a refused and a revoked key, a replacement key that cannot be checked (unreachable, 5xx, rate limited) and a first key saved unchecked, Linear's own error wording never reaching the page, non-hex colours, and, on a page that pretends to be a Mac (with a stand-in `security` behind the host's `runCommand`) or Linux (with a stand-in `secret-tool`), or Windows where there is no store: the key going to the Keychain and nowhere else (not the profile, the page, the console, a URL, an error text or a command line), a key from an earlier version moved at the start (once), a store that refuses (nothing kept on a Mac; the labelled plain copy on Linux, moved when the store works again; a replacement the Linux store refuses keeping the saved key and making no copy beside it), a replacement that cannot be checked, a Remove key that deletes both copies, a replacement saved before the first look at the store has finished, and Cancel (it puts the card back: the message of the last key check, the Terminal command and the typed key go, and it waits while a key is being checked or written), the key being absent from the page, the console and the network after saving, filters and remembered choices, paging, refresh by timer, rate limit, lost connection, light and dark (and the page icon's colour in the page list in both), a narrow window, and the dispose and re-apply count of listeners and styles across leaving the page and turning the plugin off and on three times.
- **A real Linear workspace** (a throwaway one made for this test: one team, one project, one saved view, about twenty issues), in the Linux desktop app with this folder installed, and the key typed only into the plugin's settings card. Seeded with every state, priorities, labels, a parent with sub-issues, issues in the project and one pull-request attachment. Seen working: connect ("Connected as …"); the board loading with real data in Linear's column order; a drag from Backlog to Todo, which Linear showed afterwards (read back through its API); the details panel (status, priority, assignee, project, labels, the pull-request chip, the description); the team picker (the workspace has one team), the project and saved-view pickers listing the real ones; the Refresh button reloading the board; an edit made outside the plugin appearing on the board by itself within two minutes (the refresh probe); a rejected key ("Linear did not accept the API key."). The page icon follows the text colour of its entry in dark and light, selected and not. Numbers that came out of it are in "Linear: what was relied on". It also found one bug, now fixed and tested: the Duplicate state type the board did not know (see above).
- **The desktop app** (Linux, WebKitGTK, `0.0.0-preview.156.1`), by hand, with the fake Linear served over HTTPS through a local CONNECT proxy (`test/real-app/`): Git import of this folder from a branch (the importer lists it as `megatech.linear`, with its discovery category and tags), the install review ("Connect to https://api.linear.app"), enabling, the settings card (a real `plugin_host_request` to the fake: "Connected as …"), the board, a drag in WebKit, the details panel, an update from a newer commit (the plugin stayed enabled, the key stayed, the board came back), an app restart (the key and the last team were kept), and light and dark. One bug came out of it and is fixed: WebKit needs `-webkit-user-select: none`, or a drag highlights the text it passes over.
- **The key stores in the same Linux app, with the real Secret Service** (gnome-keyring, `secret-tool` 0.21.4) and the throwaway workspace, the key read from the vault straight into the card: the update asked to approve the new commands, each listed with every argument. Save: the card says the key is kept in the system secret store, `secret-tool lookup` returns it (compared by hash with the vault's), and the app's `localStorage` (its sqlite file, read for the row, not the value) has no key. After an app restart the board loads with the key from the store. **Remove key**: `secret-tool lookup` exits 1 and the card is empty. With `secret-tool` not on the app's `PATH` (the program missing, which the plugin cannot tell from a stopped Secret Service): Save keeps the key in `localStorage` (a row of the right length appears), the card says it is plain text and why, and the board works; starting the app again with the normal `PATH` moved the key to the Secret Service (hash equal) and removed the plain row, which is the real migration. The key was removed afterwards. The first, Keychain-only version of this change was also run in the app: the update asked for the three `security` commands and the card was the labelled fallback.
- The fake Linear (`test/fake-linear/`) runs graphql-js against Linear's real schema, so it enforces the types, but its **data and behaviour are invented**.

An independent read-through of the code (a reviewer with no part in writing it) found nine bugs: a team switch or key change during a load could leave the board on "Loading…" for good, Refresh after a failed first load did the same, a slow read could undo a finished move, a deleted saved view broke the board, a drop outside the board still moved a card, a drag could stick after a release outside the window, a slow key check could delete a newer key, and cached details never refreshed. Each is fixed and has a test that fails on the earlier code.

## What was not verified

- **The macOS Keychain path has never run on a Mac.** The save, the read-back, the move out of the profile and the deletion are tested against a stand-in `security` that follows the documentation and Apple's source (see "The key and the Keychain"). Not seen on a Mac: that `add-generic-password … -w` reads the two lines from standard input when Buzz has no terminal (and what it does when Buzz was started from one), that reading an item `security` made needs no prompt, and the five-second deadline on a first read. If any of it differs, the read-back turns it into "not kept" and the card shows the Terminal command.
- **What Linear returns for a key without Write access.** Not tried: it needs a read-only key, and the only key used was a full personal one. A refused move would show the same rollback and message as any other refusal.
- **What Linear's own GitHub integration writes into an attachment's `metadata`** for a real pull request (the test workspace has no integration); the PR chip's state and draft badges rest on the documented fields.
- **A workspace on another data region.** Linear documents one API host for every region and the manifest's one origin worked for the test workspace, but that workspace sits in the default (US) region; an EU-hosted one was not used.
- **Linear's own board**, for the direction it sorts `sortOrder` in: only seen from the API (see above).
- That **Open in Linear** opens a browser: the link is there with the right address, and the click does not navigate the app's own window, but the test VM has no browser to receive it.
- macOS WebKit (WKWebView) and Windows. The web harness is Chromium only and the desktop run was Linux only.
- Touch input (dragging is mouse and pen only).
- Keyboard use beyond Tab, Enter, Space and the **Status** menu: every card is a tab stop and there are no arrow keys between cards or columns.
- The dragged copy is `position: fixed`; a host ancestor with a CSS transform would offset it. None does today.
- Markdown in descriptions is shown as plain text with links made clickable. Seen in the real workspace: Linear hands back lists with `*` markers and links as `[text](<url>)`, so the details show those characters as they are (the address inside is still a working link).
- Large workspaces: only columns of a few dozen to a few hundred cards were tried.
