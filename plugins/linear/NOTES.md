# Linear for Buzz: notes

What the plugin API reaches for a board like this, how it was tested, and what was not. Written against block/buzz-app at commit `c2210b45` (main, 2026-10-23) and the Linear GraphQL schema at linear/linear `618a737a` (2026-10-21).

## Verdict

A working board fits inside the documented API with very little reaching into the page: one page, one settings card, the host's HTTP client for Linear, and `localStorage` for the key. The gaps are the usual ones (no plugin storage, no credential store, no drag service, no stylesheet service) and each has a small, tagged workaround.

## What goes through the plugin API

| Need | Route |
| --- | --- |
| A page in the sidebar, with an icon | `ctx.pages.register({ primary: true, layout: "workspace", icon })`. The icon is a one-shape, one-colour board of three columns as a `data:image/svg+xml` URL (API v1 ships no assets); see the next table for how it takes the theme's colour |
| A place for the key | `ctx.settingsCards.register({ group: "Plugins" })` |
| Reaching Linear | `ctx.host.request` with `host.networkOrigins: ["https://api.linear.app"]` in the manifest. HTTPS only, that exact origin, no redirects, 1 MiB request body, 16 MiB response, 30 s deadline. The `Authorization` header is allowed |
| Opening the settings card from the page | `ctx.navigation.open({ version: 1, kind: "settings", section: "megatech.linear/settings" })` (a grouped card's section id is `plugin/card`) |
| Light and dark | Host CSS tokens (`--surface-base`, `--surface-panel`, `--border-standard`, `--text-standard`, `--text-metadata`, `--affordance-row-hover`, `--green-9`, `--purple-9`, `--red-9`, `--amber-9`), so the board follows Settings, Appearance with no listener |
| Opening Linear and GitHub | Plain `<a target="_blank" rel="noopener noreferrer">`, as the bundled pages do |

## What is outside the API, and what we do

All tagged `[DOM]` or noted in the code.

| Need | Why there is no API route | What we do |
| --- | --- | --- |
| Stored data (key, last team and filter) | "Plugin-specific persistent data has no host API yet", and the host has no credential store | `localStorage`, keys `megatech.linear.api-key.v1` and `megatech.linear.board.v1`. The key is plain text in the app profile and readable by any other plugin; the README says so |
| Styles | API v1 has no separate CSS | One `<style data-megatech-linear>` added and removed inside `ctx.effect` |
| Drag and drop | No drag service. HTML5 drag events work (Buzz turns `dragDropEnabled` off) but give no control over the dragged copy, scrolling or cancel | Pointer events on `window` while a press is held, a threshold, a floating copy of the card, edge auto-scroll, Escape to cancel, and the click that ends a drag suppressed. Mouse and pen only; touch scrolls. A keyboard route is the **Status** menu in the details |
| Clearing a text selection while dragging | The host has no selection service | `getSelection().removeAllRanges()` while a drag moves, behind `-webkit-user-select: none` (WebKit needs the prefix) |
| The page icon in the theme's colour | The host draws a page's `icon` as an `<img src="data:…">`, and an image cannot take `currentColor` from the page | One rule in the plugin's `<style>`, matching only an `<img>` whose `src` is exactly this plugin's icon: it paints the same shape through a CSS mask in the entry's text colour and moves the image's own pixels out of its box. If a later host draws the icon another way the rule stops matching and the icon is simply a plain dark one. (The MEGATECH lockup in the page header is ordinary page content and is not affected.) |
| Colours of the brand | Tokens carry no brand | Cyan `#00d4ff` on dark and `#0090b8` on light, chosen by the host's `data-color-mode` attribute |

## Linear: what was relied on

- Auth: a personal API key goes in `Authorization` as is. `Bearer` is for OAuth tokens. **Confirmed against a real workspace:** the key as is is answered with 200; the same key behind `Bearer` is refused with HTTP 400 and the code `INPUT_ERROR` (not 401), which the plugin shows as "Linear did not accept the API key." like any other refusal.
- **A pasted key is checked before it is kept.** Linear is asked first. A key it refuses is never saved. When a key is already saved and Linear cannot be asked (unreachable, a 5xx, rate limited), the saved key stays, nothing is saved and the card says "Your saved key is unchanged; try again"; only when there is no key yet is a key saved unchecked, and the card says so. Seen in the real app with the host blocked by a local proxy: see "What was verified".
- **Errors shown are fixed text.** Whatever Linear says in a GraphQL error (`message`) is never read, let alone shown: a service's error text can repeat what it was sent, the key among it. Each kind of failure has its own sentence in `client.ts`, and a test fakes a reply that echoes the key and checks it appears nowhere (the error, the board's notice, the page, the console).
- **Colours from Linear** (labels, projects, states) go into a `style` or an SVG attribute only if they are `#rgb`, `#rrggbb` or `#rrggbbaa`; anything else (a `url(...)` would be a remote image) is drawn in a neutral grey. Linear sends hex, so this is defence only.
- Every document is validated against Linear's published schema in a unit test, so field and variable-type mistakes fail before a user sees them. `IssueFilter` ids are `ID`, while `team(id:)` takes `String!`, so `TeamSetup` has two variables.
- One request per column (`issues(filter: team + state [+ project])`, 50 a page, newest change first) rather than one big list, so a long Done column cannot starve the others and each request stays small. (Whether each stays under Linear's complexity limit is not confirmed; see below.) A saved view goes through `customView(id).issues`, so Linear applies the view's own filter.
- The refresh timer asks one cheap question (`issues(filter: team + updatedAt > watermark, first: 1, orderBy: updatedAt, includeArchived: true)`) and reloads only on a yes. The watermark is the largest `updatedAt` seen so far, from loaded issues, from the plugin's own moves and from the probe's answer, so clock skew cannot cause a loop, the plugin's own moves are not news, and a change outside the chosen project or beyond the loaded page triggers one reload, not one a minute. An empty board has nothing to measure against and uses the local clock minus a minute. Ticks closer than two seconds apart count once (the window coming back fires several events).
- A read that began before a move cannot undo it: every move bumps a counter, and a load keeps any card moved after the load began. A saved project or view that no longer exists drops back to all issues with a note.
- Sub-issue progress is the sub-issues of state type `completed` over all that are not `canceled`. PR chips come from GitHub attachments whose URL is `…/pull/<n>`; the state of a PR is read from `metadata.status` and `metadata.draft`. **Checked in a real workspace:** an attachment made through the API with a `github.com/…/pull/<n>` URL has `sourceType: "unknown"` (so the plugin finds PRs by URL, never by `sourceType`), and the `metadata` sent with it comes back unchanged, so the chip and the details show it. **Not checked:** what Linear's own GitHub integration writes into `metadata` for a real pull request, since the test workspace has no GitHub integration.
- Ordering inside a column is the issue's `sortOrder` ascending for open states and `updatedAt` newest first for Done, Canceled and Duplicate. **Observed in a real workspace:** a newly created issue, and an issue moved to another state through the API, gets a `sortOrder` lower than the others in its state (for example -848, then -1919, then -3838 for three created in a row, against 81 for the first), so ascending order puts the newest at the top, as the board does. What was not seen is Linear's own board: no browser session on Linear's site was used, so "lowest first" there is inferred from new issues arriving at the top, not looked at.
- **Duplicate is a state type of its own.** Every new workspace has a state named Duplicate, and the API gives it the type `duplicate` (the schema lists it beside the other six) and lists it first, before Backlog. The board puts it last, orders it by last change like Canceled, leaves duplicates out of sub-issue progress, and draws it with Canceled's glyph; a state type it has never heard of sorts after the known ones instead of scrambling them. **Checked in a real workspace:** an issue cannot be created in it, and a move into it is refused ("missing duplicate relation"): Linear puts an issue there only when it is marked a duplicate of another (an `issueRelationCreate` of type `duplicate` did exactly that, with no state change sent). So the board does not send that move: a drop on the Duplicate column says why, and the Status menu shows Duplicate greyed out.
- **Cost and limits, measured with a personal key in a real workspace.** `X-Complexity` was 17 for one column request (Todo, 8 issues, `first: 50`), 3 for the refresh probe and 412 for the team setup (states, projects and views). The headers `X-RateLimit-Requests-Limit` and `-Complexity-Limit` said 2,500 requests and 3,000,000 complexity points per hour, and the `-Reset` headers are milliseconds since the epoch (the plugin reads seconds or milliseconds). A board load is one setup request and one per column; an idle board costs one probe a minute, so about 60 requests an hour.

## What was verified, and how

Run against the code in this folder. CI (`.github/workflows/linear-tests.yml`) runs only the type check and the unit tests; everything else below is run by hand.

- `pnpm test` (vitest, 74 tests): the client (headers, error kinds, fixed error text, no key in any error text, even from a reply that echoes it), what is done with a pasted key when Linear can or cannot be asked, colours from Linear, the store (load, paging, filters, optimistic move and rollback, refresh rules, stale answers dropped, blocked states, no request for a move into Duplicate, no tick before the time Linear gave after a rate limit), the column order and the progress count with the Duplicate type and an unknown one, the page icon and its mask rule, and every GraphQL document against Linear's schema.
- `test/run.sh <block/buzz-app checkout>`: 36 browser tests in Buzz's own production web build (headless Chromium, fixture relay), with the plugin registered the way an installed one is. They cover the columns and their order (Duplicate last), drag (including Escape, a refused move and a drop on Duplicate), the details panel and its keyboard route (Duplicate greyed out in the Status menu, and greyed out as a target while a card is held), the connect-and-save flow, a refused and a revoked key, a replacement key that cannot be checked (unreachable, 5xx, rate limited) and a first key saved unchecked, Linear's own error wording never reaching the page, non-hex colours, the key being absent from the page, the console and the network after saving, filters and remembered choices, paging, refresh by timer, rate limit, lost connection, light and dark (and the page icon's colour in the page list in both), a narrow window, and the dispose and re-apply count of listeners and styles across leaving the page and turning the plugin off and on three times.
- **A real Linear workspace** (a throwaway one made for this test: one team, one project, one saved view, about twenty issues), in the Linux desktop app with this folder installed, and the key typed only into the plugin's settings card. Seeded with every state, priorities, labels, a parent with sub-issues, issues in the project and one pull-request attachment. Seen working: connect ("Connected as …"); the board loading with real data in Linear's column order; a drag from Backlog to Todo, which Linear showed afterwards (read back through its API); the details panel (status, priority, assignee, project, labels, the pull-request chip, the description); the team picker (the workspace has one team), the project and saved-view pickers listing the real ones; the Refresh button reloading the board; an edit made outside the plugin appearing on the board by itself within two minutes (the refresh probe); a rejected key ("Linear did not accept the API key."). The page icon follows the text colour of its entry in dark and light, selected and not. Numbers that came out of it are in "Linear: what was relied on". It also found one bug, now fixed and tested: the Duplicate state type the board did not know (see above).
- **The desktop app** (Linux, WebKitGTK, `0.0.0-preview.156.1`), by hand, with the fake Linear served over HTTPS through a local CONNECT proxy (`test/real-app/`): Git import of this folder from a branch (the importer lists it as `megatech.linear`, with its discovery category and tags), the install review ("Connect to https://api.linear.app"), enabling, the settings card (a real `plugin_host_request` to the fake: "Connected as …"), the board, a drag in WebKit, the details panel, an update from a newer commit (the plugin stayed enabled, the key stayed, the board came back), an app restart (the key and the last team were kept), and light and dark. One bug came out of it and is fixed: WebKit needs `-webkit-user-select: none`, or a drag highlights the text it passes over.
- The fake Linear (`test/fake-linear/`) runs graphql-js against Linear's real schema, so it enforces the types, but its **data and behaviour are invented**.

An independent read-through of the code (a reviewer with no part in writing it) found nine bugs: a team switch or key change during a load could leave the board on "Loading…" for good, Refresh after a failed first load did the same, a slow read could undo a finished move, a deleted saved view broke the board, a drop outside the board still moved a card, a drag could stick after a release outside the window, a slow key check could delete a newer key, and cached details never refreshed. Each is fixed and has a test that fails on the earlier code.

## What was not verified

- **What Linear returns for a key without Write access.** Not tried: it needs a read-only key, and the only key used was a full personal one. A refused move would show the same rollback and message as any other refusal.
- **What Linear's own GitHub integration writes into an attachment's `metadata`** for a real pull request (the test workspace has no integration); the PR chip's state and draft badges rest on the documented fields.
- **A workspace on another data region.** Linear documents one API host for every region and the manifest's one origin worked for the test workspace, but that workspace sits in the default (US) region; an EU-hosted one was not used.
- **Linear's own board**, for the direction it sorts `sortOrder` in: only seen from the API (see above).
- That **Open in Linear** opens a browser: the link is there with the right address, and the click does not navigate the app's own window, but the test VM has no browser to receive it.
- macOS WebKit (WKWebView) and Windows. The web harness is Chromium only and the desktop run was Linux only.
- Touch input (dragging is mouse and pen only).
- Keyboard use beyond Tab, Enter, Space and the **Status** menu: every card is a tab stop and there are no arrow keys between cards or columns.
- The dragged copy is `position: fixed`; a host ancestor with a CSS transform would offset it. None does today.
- Markdown in descriptions is shown as plain text with links made clickable. Seen in the real workspace: Linear hands back lists with `*` markers and links as `[text](<url>)`, so the details show those characters as they are (the address inside is still a working link).
- Large workspaces: only columns of a few dozen to a few hundred cards were tried.
