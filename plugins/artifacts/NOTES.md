An SVG in an `<img>` is its own document, so `currentColor` in it does not inherit the app's colour: the plugin's earlier icon drew black. The plugin API has no theme-following icon, so the plugin registers none. Measured in the Buzz 1.0 Linux app (`0.0.0-preview.156.1`): the darkest pixel of an idle entry's icon in light was 63 for Inbox, 63 for the generic icon (sidebar), 82 for Reminders and 81 for the generic icon (top bar), against 0 for the earlier icon; in dark the brightest pixel was 199 for Inbox, Reminders and the generic icon alike.

## Choices

- **The page renders the View itself**, rather than registering a panel. The documented panel route (`ctx.panels.register` with `matches`) opens when a link is clicked in a message, and the API gives a page no documented way to open a panel for a target of its own; the docs say other pages "can use these same contracts with their own layout". If Block adds a page-to-panel opener, switch to it so the page is only the list.
- **No build step.** The plugin is small enough to be one hand-written `plugin.js`, like `key-probe`. The list logic is exported (`createLinkStore`, `checkUrl`) so the tests import it; the host reads only `inject` and `apply`.
- **Storage name `claude`** is fixed, as asked. See the README on what that shares.
- **Plugin storage**: "Plugin-specific persistent data has no host API yet" (docs/building.md §1), so `localStorage` under the plugin id.
- **The default page** is a second key, `megatech.artifacts.default`, holding only the page's id. The list's own JSON is untouched, so old data reads as it did, and the first page is the default until one is saved. The store writes the default that applies at every change (so a stale id is repaired on the next save), and reads it as "the saved id if that page exists, else the first page".
- **A hand-picked page stays while the page is open.** The page opens on the default; a clicked chip is remembered only in the page's own state. Changing the default from the Settings card while the page is open behind it does not move the page the user chose; opening the page again loads the new default (checked in the Linux app). If that proves surprising, make the page follow the default whenever it changes.

- **One top-bar page per pinned page, in a child scope.** The alternative, registering every saved page and hiding some, does not exist: a registered primary page is always listed. Each pinned page is `ctx.plugin({ inject: ["pages"], apply })` and unpinning disposes the fiber. A title is fixed at registration, so a rename disposes the entry and registers it again; the page's selection is kept (the shell identifies the page by its id, which does not change), checked in the Linux app.
- **One round at a time.** The same page id cannot be registered while the old registration is still listed and disposal is asynchronous, so a change is applied only after the previous one has finished, and one that arrives meanwhile triggers another round. This is what the rapid-change tests pin down.
- **The pinned page is only the page.** It renders `browser.View` for its own saved page and has no chip bar, no controls and no state. Pinning and unpinning are on the Artifacts page's chip bar and in the Settings card.
- **Page ids** are `pin-` plus the saved id. Saved ids made by this plugin are lowercase letters, digits and `-`, so they always fit; an id from a hand-edited list that could not make a valid page id cannot be pinned, and one in a saved pin list is dropped.
- **Unpinning or removing the page you are looking at.** The shell keeps the page's address in its history. When Settings (a dialog over the page) closes after the entry is gone, it shows its own "This destination couldn't open ... Your target has been kept for retry" notice with Retry navigation and Open Settings; pinning the page again made the shell reopen it by itself. Navigating away first through `ctx.navigation` (`inject: ["navigation"]`, `docs/plugin-architecture.md` "Navigation targets and visits") would not cover the Settings-over-the-page case, and it would pull the user out of what they are doing, so the plugin leaves the shell's behaviour as it is and the README says so.

## The Settings card, redesigned

- **Surfaces from the host, accents on top.** Surfaces, text, borders and focus keep coming from the host's tokens (so light and dark need no listener); the card's own look is a set of named custom properties on its root. That departs from `docs/building.md` §2 ("never hard-code a colour") on purpose, only for the accents, and only on the card's root.
- **Light theme.** The bright cyan is 1.8:1 on white. Text and every line that means something (the default's border and bar, input and control edges, the marks, focus) use darker inks in light (`#00708f`, `#c4009f`, `#c2362b`), and in dark the edges are the brand cyan and magenta at higher alpha, so all of them are at least 3:1. These inks are derived for this plugin, not read from a palette. The bright cyan stays on the Add button's fill and on decoration.
- **One font is embedded** (the latin subset of Chakra Petch Bold, SIL OFL 1.1, notice in `licenses/`): a plugin cannot load fonts, and the file grows by about 13 KB of base64. Addresses and labels use the system monospace. A second font, Share Tech Mono, was dropped: its licence declares a Reserved Font Name ("Share"), and an embedded subset is a modified version that would need permission to keep it.
- **Rename is in place and Remove asks once.** The name is text, not an always-open field, so nothing can change width when the default moves. Esc leaves the editor or the question and must not reach Settings, which closes on Esc (checked in the app), so those handlers stop the event. Focus: the rename field and the safe answer (Keep) take it when they appear; Save, Cancel and Keep give it back to the button that opened them. Confirming Remove moves the focus **before** the card goes (`removePage` in `ArtifactsSettings`): to the Rename button of the next card, else the one before, else (no card left) the first field of the add form, so it is never left on the button that goes away, which would drop it to the page's body. A card that has no Rename button on screen at that moment (it is being renamed or asked about) is skipped. Each card's Rename button registers itself by saved id with a callback ref, the way the chips do. Checked in the Linux app (`0.0.0-preview.156.1`) for the middle page, the last page and the only page left.
- **Smaller fixes made with it.** The chip bar's default star takes the chip's text colour (the accent was about 1.6:1 on white). After **Make default** on the chip bar, the focus goes to that page's chip, because the button it was on goes away. The Pin button is not shown for a saved id that could not make a page id (a hand-edited list), on the card and on the chip bar, rather than doing nothing. A saved name of only blanks is shown as the page's address everywhere, including the top-bar entry (the fallback is now tested).
- **A narrow window** is handled with container queries on the card's own root (600 px and 420 px), not media queries, because the card's width depends on the Settings dialog.
- **Tests.** `test/harness.mjs` holds a small stand-in for React that keeps `useState` and `useRef` by position in the tree, so a test can press Rename and then look at the card. The stand-in has no focus, so a ref is given a fake element with a `focus()` that counts. Real focus, `autoFocus` and Esc reaching the Settings dialog are checked by `test/web/artifacts.spec.mjs`, in Buzz's own web build (`test/run.sh`); the repository's CI runs it too, in `artifacts-browser-tests.yml` (the same block/buzz-app commit as the Vim workflows; the first step of the three workflows fails when their `BUZZ_APP_REF` differs), next to the node tests. The store tests stay in `links.test.mjs`; everything that mounts the plugin is in `apply.test.mjs`.

## Not verified

Run since in the Buzz 1.0 Linux app (`0.0.0-preview.156.1`), where `ctx.browser.available` is false: the chip bar, the page's macOS-only message, the Settings card, the sidebar entry, the default's marking and the ways of changing it were seen working. Still unconfirmed, because they need the macOS app: the page layout with a real `browser.View` under the chip bar, whether the Settings `ui-button` class styles a button there (on Linux the buttons render as plain text), the default page loading on open, and the sign-in persistence.

Pins, run in the same Linux app and seen working: the Pin to top bar / Unpin controls in the Settings card and on the page, the entry appearing and going at once, its place among Buzz's own entries, a click opening the page, a rename carrying over to the entry (the open page stays open), a removed page's entry going, the pins surviving a restart, and the **More pages** menu in a narrow window. Not verified: a Buzz older than d5d414d4 (the sidebar fallback is from the documentation), the top bar on macOS, and a real `browser.View` in a pinned page.
